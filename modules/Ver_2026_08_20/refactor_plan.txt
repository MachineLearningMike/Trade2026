Generic (model, label) TRAIN / INFER framework
Draft: 2026-08-29

GOAL
----
Make TRAIN and INFER a framework that is *generic over declared (model, label)
tuples* (and ensembles of those tuples), without label-specific CLI sprawl,
inconsistent option sets, or silent no-ops when a pair is incompatible.

Prove that genericity by accommodating as many *existing* models and labels
as practical in the first cut (see §0). Breadth is intentional: every pair
we host early is a stress test; skipping pairs leaves untested assumptions
and raises the chance the framework is not actually generic enough.

This is NOT a claim of total domain generality. data.py intentionally assumes
crypto / market windowed time series and a small set of fixed normalization
modes (see §2.6): **two-layer** (intra- then inter-window) and **one-layer**
(global). Genericity stops at the (model, label) product and sample
pack/unpack contracts — not at arbitrary ML data modalities.

New code lives in:  modules/Ver_2026_08_30/
This file is the working plan; freeze Ver_2026_08_20 as the known-good baseline.

2.5 Opaque sample dict (pack / unpack)
--------------------------------------

Problem today:
  Dataset / trainer / INFER all hard-code the tuple
      (x, p, mean, std, shape, y)
  so every new label or aux field ripples through TRAIN, INFER, trainer,
  collate helpers, and error-ensemble.

Decision (chosen): FULLY OPAQUE SAMPLE DICT
  - __getitem__ returns a dict assembled by LabelSpec.pack_sample.
  - TRAIN / INFER / ResumableTrainer never destructure mean/std/shape/y.
  - ModelSpec.unpack_input(sample) reads only forward kwargs.
  - Feature-side moments (mean/std/shape) are COMPUTED by data FeaturePrep
    (see §2.6), then INCLUDED into the dict by the label when packing —
    labels do not reimplement FiLM moment math.

Train / infer loops:

  for sample in loader:                         # opaque dict
      pred = model(**model_spec.unpack_input(sample))
      loss = loss_fn(sample, pred)              # label unpacks inside

loss_fn (compose):

  def loss_fn(sample, pred):
      target = label.unpack_target(sample)
      base = label.loss(pred, target)
      return model_spec.wrap_loss_terms(base, sample, pred)

----------------------------------------------------------------------
FEATURE NORMALIZATION — understood design (authoritative)
----------------------------------------------------------------------

Config (exact names):
  "normalization": "one-layer" | "two-layer"
  Code home: data.FeaturePrep
  Replaces today's boolean normalize_window. Default: "two-layer".

Domain honesty:
  data.py assumes windowed market/crypto series. FeaturePrep is fixed
  domain prep shared by all labels — not a fully generic data framework
  and not forked per label.

What "layer" means:
  one-layer  — one global norm of the raw series (dataset-wide SharedStats).
  two-layer  — (1) intra-window norm of x by that window's moments, then
               (2) inter-window norm of those moments by one shared
               inter-stats object. Invented composition for long-span crypto.

Why two-layer is the default (and when one-layer fails):
  BTC-like prices can drift by large factors over years (e.g. ~2x+).
  Fitting one global mean/std on years-spanning data makes σ_global huge.
  Local window variance then shrinks toward near-zero in normalized space;
  short-horizon structure is lost.

  Two-layer avoids might-be-large local mean_w / std_w *inside the path
  tensor x* by factoring them out:
    - Intra: x = (x_raw - mean_w) / std_w
      → absolute level/scale leave x; local shape stays O(1).
    - The large mean_w / std_w are NOT discarded; they move to moment
      channels, then are made comparable via inter-window norm:
        mean_n = (mean_w - E[mean_w]) / Std[mean_w]
        std_n  = (std_w  - E[std_w])  / Std[std_w]
      Absolute largeness is absorbed into the shared inter-stats
      (both E[·] *and* Std[·], not E alone). The model sees
      (x, mean_n, std_n[, shape_n]), never raw (x, mean_w, std_w).

Sensitivity (do not treat moments as trash):
  Intra-window stats (mean_w, std_w, shape_w) are more sensitive /
  regime-informative than individual samples inside the window. After
  whitening x they are first-class conditioning (FiLM), not disposable
  byproducts. Dropping them after intra-window norm would throw away
  the local level/vol summary two-layer was designed to preserve.

Shared-stats invariant (BOTH modes):
  The normalized sample always refers to exactly ONE frozen train-fitted
  SharedStats. Denorm / checkpoint resume / infer must reload that same
  object. Modes differ in payload and *which* SharedStats — not in
  whether stats are shared.

  one-layer:
    Payload:     x_n  (+ any globally-normed conditioning)
    SharedStats: global (mean, std[, ...]) of raw train series
    Inverse:     x_raw = x_n * std + mean

  two-layer:
    Payload:     (x, mean_n, std_n[, shape_n])
                 x already intra-whitened; mean_n/std_n are per-WINDOW
                 outputs of the shared inter-norm (NOT one scalar pair
                 for the whole dataset).
    SharedStats: inter-window
                 (E[mean_w], Std[mean_w], E[std_w], Std[std_w], ...)
                 fitted once on train windows — single shared object.
    Inverse:     mean_w = mean_n * Std[mean_w] + E[mean_w]
                 std_w  = std_n  * Std[std_w]  + E[std_w]
                 x_raw  = x * std_w + mean_w     (broadcast over time)
    Need both E[·] and Std[·] to invert; E alone is not enough.

Label y denorm is SEPARATE:
  y_raw = y_n * label_std + label_mean
  uses label SharedStats (rise_flag may be identity). Feature two-layer
  SharedStats do not restore y; label stats do not restore x.

Mechanics cheat-sheet:

  two-layer:
    for each window:
      mean_w, std_w, shape_w = moments(x_raw)
      x = (x_raw - mean_w) / std_w
    fit SharedStats on train {mean_w, std_w, shape_w}
    mean_n, std_n, shape_n = inter_zscore(moments, SharedStats)
    model input / sample keys: x, mean_n, std_n, shape_n, ...

  one-layer:
    fit SharedStats on raw train series
    x_n = (x_raw - mean) / std
    keep as ablation / short-span control; not default for long history

Ownership:
  FeaturePrep / SharedStats / WindowContext  → data.py
  Labels only consume the mode's tensors via WindowContext and pack keys
  Labels must not reimplement one-layer / two-layer math

Out of scope for first cut:
  - modality-agnostic data plugins
  - per-label alternate feature-norm schemes
  - mode names other than one-layer / two-layer

Two artifacts cross the boundary (and ONLY these):

  (1) WindowContext  — built by data, consumed by label
  (2) sample dict    — built by label.pack_sample(WindowContext, ...),
                       returned by Dataset.__getitem__

      "mean": Tensor[F],                # raw window mean (pre dataset-stat)
      "std": Tensor[F],
      "shape": Tensor[S, F],
      "mean_n": Tensor[F],              # after dataset-stat norm (FiLM)
      "std_n": Tensor[F],
      "shape_n": Tensor[S, F],
      "price_feature_idx": int,
      # optional raw recent prices for label to cut p to its length
      "prices_norm": Tensor[T],
  }

----------------------------------------------------------------------
LABELSPEC  (per-label policy + sample schema)
----------------------------------------------------------------------
Owns:
  - build_cache_row(WindowContext-like raw slices, cfg) -> LabelRow
      LabelRow = { "y_full": Tensor[...], "aux": {...} }  # e.g. h_past
  - reduce_label_stats(rows, train_indices) -> LabelStats
  - normalize_target / denorm_pred / denorm_target (policy)
  - resolve_dims / sync_output_dim / model_past_len (p length)
  - pack_sample(ctx: WindowContext, row, label_stats) -> dict
      * copies/selects feature keys from ctx that THIS label's COMPAT
        models need (typically x, p, mean_n, std_n, shape_n)
      * cuts p to label.resolve_model_past_len
      * writes y (sliced + normalized per policy) + label aux keys
  - unpack_target(sample) / collate / loss / metrics / viz
  - label_signature() + label_cache_version for dataset_signature / cache
  - provided_sample_keys for COMPAT checks vs ModelSpec.required_input_keys

Does NOT own:
  - loading Total / Binance / macro
  - computing window mean/std/shape FiLM moments (FeaturePrep in data)
  - split indices / DataLoader threading
  - importing model.py

----------------------------------------------------------------------
HANDSHAKE (who calls whom)
----------------------------------------------------------------------

  # cache build (once)
  for idx in all_samples:
      raw = data.slice_raw(idx)                  # prices, x_raw, windows
      feat = data.feature_prep.compute(raw)      # mean/std/shape, x_n, ...
      row  = label.build_cache_row(raw, cfg)     # y_full + aux (h_past, ...)
      store feature columns + label payload
  feat_stats  = data.feature_prep.reduce_stats(train)
  label_stats = label.reduce_label_stats(rows, train)
  data.write_cache(envelope + label.serialize_payload(...))

  # __getitem__
  ctx = data.make_window_context(idx)            # FeaturePrep fields filled
  row = data.label_payload[idx]
  sample = label.pack_sample(ctx, row, label_stats)
  return sample                                 # opaque dict

  # train/infer
  pred = model(**model_spec.unpack_input(sample))
  loss = label.loss(pred, label.unpack_target(sample))  # via compose

2.7 Ensembles of (model, label) — and what "ensemble_label" is
--------------------------------------------------------------

Requirement:
  The TRAIN/INFER × (model, label) × data framework must also host a
  *model* that is itself an ensemble of existing atomic (model, label)
  tuples (TelePred delay bank, ErrorEnsemble stages, and later arbitrary
  stacks).

User decision:
  An ensemble model does NOT need a true supervised label.
  If anything is called ensemble_label, it is only a COLLECTION of the
  member labels — not a new find/loss target family like yield/trend.

----------------------------------------------------------------------
Atomic vs ensemble slots
----------------------------------------------------------------------

  Atomic unit (unchanged from §2.2–2.6):
      pair = (ModelSpec_atomic, LabelSpec_true)
      LabelSpec_true has find / loss / pack_sample / metrics.

  Ensemble unit:
      ensemble_model = EnsembleModelSpec(
          members = [ (model_i, label_i), ... ],   # each atomic & COMPAT
          fusion  = FusionSpec(...),               # how to combine outputs
      )
      ensemble_label = LabelCollection(            # NOT a true label
          members = [ label_i for each member ],
      )

  TRAIN/INFER still resolve "the active slot" as either:
      - atomic:  (model, label_true)
      - ensemble:(ensemble_model, label_collection)

  registry treats LabelCollection as a distinct kind (is_true_label=False).
  assert_compatible on an ensemble checks EACH member against COMPAT,
  then checks ENSEMBLE_KINDS constraints (e.g. error ⇒ identical point
  labels + regression).

----------------------------------------------------------------------
What LabelCollection is / is not
----------------------------------------------------------------------

  IS:
    - ordered bag of member LabelSpecs (and stable member ids)
    - pack_sample(ctx) -> dict that NAMESPACES member samples:
          {
            "features": {...},          # optional shared feature view
            "members": {
               "m0": label_0.pack_sample(ctx, row_0, stats_0),
               "m1": label_1.pack_sample(ctx, row_1, stats_1),
               ...
            },
            "fusion_meta": {...},
          }
    - metrics/report that iterate member metrics + fusion metrics
    - signature fragment = hash of member label_signatures

  IS NOT:
    - a find() that invents a new joint y for the ensemble as a whole
    - a single loss replacing member losses (unless FusionSpec explicitly
      declares a joint train objective later)
    - something data.py special-cases with if ensemble_label == ...

  So: ensemble_label := collection(member labels), never a parallel
  Label_Yield-style class.

----------------------------------------------------------------------
Where training vs inference live
----------------------------------------------------------------------

  Member TRAINING (default path — matches TelePred & ErrorEnsemble today):
    - Loop members (or stages/delays).
    - Each iteration is a normal atomic train_one_run(model_i, label_i)
      on shared data WindowContext plumbing.
    - data.py still sees ONE true LabelSpec per run (the member's).
    - EnsembleModelSpec / LabelCollection are NOT required inside
      train_one_run for this path.
    - compose.ensemble_train owns the loop + checkpoint layout.

  Ensemble INFERENCE / reporting (where collection matters):
    - Load EnsembleModelSpec + all member checkpoints.
    - data builds one WindowContext.
    - LabelCollection.pack_sample builds the namespaced sample dict
      (or compose builds per-member sample views from the same ctx).
    - EnsembleModelSpec.forward(sample):
          for each member:
              pred_i = model_i(**model_i.unpack_input(sample_i))
          return fusion.combine(pred_i, ...)
    - Metrics: per-member via label_i, plus fusion-level numbers
      (e.g. ErrorEnsemble en_k in y-space; TelePred bank curves).

  Optional later: joint training through FusionSpec.loss(sample, preds)
  — still does not make LabelCollection a true label; joint loss lives
  on FusionSpec.

----------------------------------------------------------------------
Specializing today's ensembles
----------------------------------------------------------------------

  TelePred (--ensemble):
    members = [(model, label) @ delay d for d in delays]
    label_relation = identical  ⇒ LabelCollection of N references to
      the SAME LabelSpec (delays differ in WindowContext / telepred,
      not in label identity)
    fusion = delay_bank (report / optional blend; train is per-d)

  ErrorEnsemble (--error-ensemble):
    members = [(regression, label) @ stage s for s in 0..n-1]
    label_relation = identical AND label in {trend, yield, rise_flag}
    fusion = sum residuals in y-normalized space (error_ensemble_logic.txt)
    train = sequential atomic runs with residual targets derived by
      compose/error_ensemble (stage target is still the SAME LabelSpec
      space; residual math is FusionSpec/stage plumbing, not a new label)

  Stack (future general ensemble):
    members = arbitrary COMPAT atomic pairs (may be heterogeneous labels)
    ensemble_label = LabelCollection(those labels)
    fusion = user FusionSpec (weighted sum, gating, etc.)
    data: one WindowContext; each member label packs its own view
    (may require per-member label caches if find() differs)

----------------------------------------------------------------------
data.py interaction under ensembles
----------------------------------------------------------------------

  - FeaturePrep / WindowContext stay shared across labels (domain-fixed
    two-layer | one-layer modes), not per-ensemble.
  - Per atomic train run: data binds self.label = member LabelSpec_true
    (unchanged §2.6).
  - Per ensemble infer: data (or compose) binds self.label =
    LabelCollection; pack_sample dispatches to members. No second
    FeaturePrep. No ensemble-specific moment math.
  - Heterogeneous member labels ⇒ possibly multiple label payloads /
    caches keyed by member id; feature cache still one.

----------------------------------------------------------------------
Dependency sketch (ensemble)
----------------------------------------------------------------------

  LabelSpec_true (atomic)          FusionSpec
         ▲                              ▲
         │                              │
  LabelCollection ─────────────── EnsembleModelSpec
   (bag of labels)                 (bag of (model,label) + fusion)
         ▲                              ▲
         └────────── compose ───────────┘
                       ▲
                  TRAIN / INFER

  TRAIN atomic member:   compose → (model_i, label_i, data)
  TRAIN ensemble bank:   compose loops atomic member trains
  INFER ensemble:        compose → (EnsembleModelSpec, LabelCollection, data)

----------------------------------------------------------------------
Rules of thumb
----------------------------------------------------------------------
  - Need a y to supervise one network head? → true LabelSpec.
  - Need to group several already-defined (model, label)s?
      → EnsembleModelSpec + LabelCollection (ensemble_label).
  - Never invent Label_ErrorEnsemble / Label_TelePred as find/loss
    families; those are ensemble kinds + FusionSpec.
  - COMPAT applies to members; ENSEMBLE_KINDS applies to the bag.
